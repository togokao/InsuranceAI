## 1. 產品定位與核心功能

### 1.1 三個功能形成一條銷售流程

```
新聞彙整 ──→ 開啟話題 ──→ 需求問卷 ──→ 保單媒合 ──→ 建議書簡化 ──→ 成交
  (拉近關係)              (了解客戶)    (挑商品)      (說服客戶)
```

另外需要一個**輕量客戶管理**把三個功能串起來，記錄客戶的興趣標籤、已有保單、問卷結果和互動紀錄。

### 1.2 每日新聞彙整
- 每天早上排程抓 RSS（健康、投資、保險新聞），用 AI 產生摘要、分類，加上「聊天切入點」。
- 分成**業務員版**（含話術）與**客戶版**（精簡圖卡），客戶版可以一鍵分享到 LINE。
- 依客戶的興趣標籤，提示哪些客戶可能對這則新聞有興趣。
- 風險：
  - **版權**：只放摘要和原文連結，不轉載全文。
  - **投資新聞**：業務員一般沒有投顧執照，不能寫成投資建議，分享時要自動附上免責聲明。

### 1.3 建議書簡化（價值最高，風險也最高）
- 把建議書簡化成 1～2 頁圖文說明：保障一覽、情境舉例、保費與解約金走勢圖、重要提醒。
- **數字由程式從 PDF 擷取，AI 只負責整理格式和改寫成白話**，產出後還要和原文交叉比對。
- **業務員必須逐欄確認**，確認完才能產生給客戶看的圖卡。
- 法規：
  - 業務員自製的簡化說明可能被視為招攬文宣，依規定通常要經過所屬公司審核。
  - 不能拿掉除外責任、等待期、提前解約損失等不利資訊，否則可能構成不實招攬。
  - 頁尾固定註明「以正式建議書及保單條款為準」。

### 1.4 需求問卷與保單媒合
- 業務員傳專屬連結給客戶，客戶不用登入，直接用手機填寫。
- 系統算出保障缺口：醫療、意外、重疾、壽險、失能、長照、退休。
- **先用規則篩選商品，再讓 AI 寫推薦理由**：篩選結果可以追溯，也解釋得清楚。
- 健康資料屬於**特種個資**（個資法第 6 條），要取得明確同意、加密儲存，並告知保存期限。
- 可以結合投資型保單本來就要做的適合度評估，減少客戶重複填寫。

## 2. 業務員身分與營運模式帶來的影響

### 2.1 跨多家公司：建議書不能靠各家寫死的解析規則

```
上傳 PDF → AI 讀取內容，填進統一格式 → 業務員逐欄確認或修正 → 產生簡化圖卡
                                     ↑
                    確認過的結果累積成各公司範本，之後辨識越來越準
```

### 2.2 保單資料庫分兩層，並做版本管理

| 層級 | 內容 | 維護者 |
|---|---|---|
| 平台共用商品庫 | 各公司商品的基本資料、條款、費率 | 平台方 |
| 保經公司設定 | 合作的保險公司、主推商品、內部備註 | 各保經公司的管理者 |

- 商品狀態分為銷售中、停售、改版。停售商品要保留舊版條款，供既有客戶查詢。
- 每個匯入來源各設一份「欄位對應」設定，不要把轉換邏輯寫死在程式裡。
- 各公司商品屬性不同的部分，用 JSONB 欄位存放。

### 2.3 多人訂閱服務要先確定的事
- **租戶層級**：保經公司 → 業務員 → 客戶，也要支援個人業務員單獨訂閱。
- **資料隔離**：在資料庫層級用 PostgreSQL 的列層級安全性（RLS）強制隔離，不只靠程式判斷。
- **客戶資料歸屬**：業務員離職時，客戶資料歸誰，要寫進服務條款。
- **法規與資安**：
  - 可能適用金管會的作業委外相關規範。
  - 資料要能存放在台灣，或可以指定雲端區域。
  - 中期要準備 ISO 27001，並提供存取紀錄和資料刪除機制。

## 3. 技術選型

### 3.1 前端：Next.js 與純 HTML+JS+CSS 比較

| 面向 | Next.js | 純 HTML+JS+CSS |
|---|---|---|
| 大量頁面的維護 | 元件可以重複使用 | 頁面越多，重複程式碼越多 |
| 狀態管理、路由、表單 | 有成熟的工具 | 都要自己寫 |
| 部署 | 要跑 Node 伺服器 | 放靜態檔案即可 |
| 學習成本 | 高 | 低 |

**結論**：這是登入後才能用的系統，不需要 SEO，Next.js 的伺服器端渲染用處不大。建議用 **Vite 加 Vue／React 做單頁應用**，部署時是靜態檔案。客戶端的新聞分享頁、問卷頁這類輕量頁面，用純 HTML+JS 做。

### 3.2 資料庫：PostgreSQL 與 Oracle 比較

| 面向 | PostgreSQL | Oracle |
|---|---|---|
| 授權成本 | 免費 | 非常高 |
| 多租戶資料隔離 | 內建 RLS | 要另外付費或自己實作 |
| 不固定的商品屬性 | JSONB 好用 | 支援，但比較笨重 |
| AI 語意搜尋 | pgvector | 只有新版本支援 |

**結論**：用 PostgreSQL。Oracle 只在大型保經公司要求「部署在他們自己的機房」時才考慮，而且也可以透過資料匯入介面對接，不必整套系統都換成 Oracle。

### 3.3 後端語言：Node.js 與 C# 比較
- **Node.js**：AI 相關套件最完整，前後端可以用同一種語言。
- **C#**：型別嚴謹、效能好，金融業 IT 部門接受度較高。
- **PDF 表格解析**：Python 的工具最強（例如 pdfplumber）。C# 常用的 iText 是 AGPL 授權，用在商業服務要留意。
- **結論**：主要 API 依團隊熟悉度選擇；PDF 解析和 AI 處理獨立成背景服務，由工作佇列觸發。

## 4. 系統架構

### 4.1 各元件的職責

| 元件 | 存放內容 |
|---|---|
| Web Server | 統一網頁入口，依角色權限顯示不同頁面 |
| PostgreSQL | **所有需要查詢、篩選或控管權限的資料**：客戶、保單、商品、費率、合作設定、主推商品、內部備註 |
| File Server（物件儲存） | **只放檔案**：條款 PDF、建議書 PDF、產出的圖卡；資料庫只記錄檔案路徑和相關資訊 |

> 修正：原本規劃把費率、合作設定、內部備註也放在 file server，但這些資料媒合時要查詢，還要依權限顯示，所以改放資料庫。

### 4.2 資料庫隔離
- **不要一位業務員一個資料庫**，否則每次修改資料表結構和備份都要做幾百次。
- 用同一個資料庫，每筆資料標記公司與業務員，再用 RLS 隔離。
- 大型保經公司若要求資料實體分開，再提供獨立資料庫，作為加值方案。

### 4.3 角色

| 角色 | 主要功能 |
|---|---|
| 平台管理員 | 維護共用商品庫、新聞來源、租戶、計費 |
| 保經公司管理者 | 管理業務員帳號、合作保險公司、主推商品、內部備註，查看用量 |
| 主管／督導 | 查看團隊統計數字，**不一定能看客戶健康資料** |
| 一般業務 | 今日首頁、新聞、客戶、建議書簡化、需求與媒合 |
| 客戶（不需登入） | 用專屬連結填問卷、查看分享內容 |

做成同一個網站，依權限顯示不同的選單，不要每個角色各做一套網頁。

### 4.4 還需要補上的元件

| 元件 | 用途 |
|---|---|
| 工作佇列 | 建議書分析、產生圖卡等耗時的背景工作 |
| 排程 | 每日新聞、備份、商品資料同步 |
| 多因素驗證（MFA） | 系統有健康資料，一定要有 |
| 稽核日誌 | 記錄誰在什麼時間看了哪位客戶的資料 |
| 備份與還原 | 資料庫和檔案都要，並定期演練還原 |
| 通知 | LINE 官方帳號或推播 |

## 5. 地端 AI 與去識別化

### 5.1 Mac mini 加 Ollama 的評估
- **一台機器分給多位業務員，實際上是大家排隊共用**：Ollama 沒有切割資源的功能，資料隔離要在應用程式層處理。
- **容量**：一份建議書約 20～50 頁，處理一份要幾十秒到幾分鐘，尖峰時段等待會很久。
- **品質**：本地模型處理繁體中文、保險術語和複雜表格，通常不如 Claude。
- **營運風險**：
  - 只有一台機器，壞了就停擺。
  - 若放在辦公室，要解決和雲端伺服器的連線，以及實體安全的問題。
  - 保經公司做資安審查時，「客戶資料在某間辦公室的 Mac mini 上處理」可能比使用正規雲端服務更難通過。
- **硬體選購**：重點是統一記憶體容量，建議 48～64GB 以上。

### 5.2 結論：先去識別化，再送 Claude，第一階段不需要 Mac mini

**去識別化流程**（用規則處理就好，不需要 AI，在 web server 上執行）：

1. 上傳 PDF，並指定這份建議書屬於哪位客戶。
2. 在本平台擷取 PDF 的文字和表格。**不送頁面圖片**；掃描版 PDF 先在本地做文字辨識（OCR）。
3. 遮蔽個資，用三種方式比對：
   - **精準比對**：用客戶管理資料裡的姓名、身分證字號、電話、地址
   - **格式比對**：身分證字號、手機、Email、日期
   - **欄位比對**：要保人、被保險人、受益人、業務員及其登錄字號
4. 把個資換成代號，例如「王美玲」換成 `[被保險人]`；生日改成「投保年齡」。
5. **送出前做安全檢查**：再掃描一次，只要還有已知個資就攔下。
6. 把遮蔽後的內容送 Claude 分析。
7. 結果回來後，在本平台把代號換回真實姓名，再產生圖卡。

**法規配套**：
- 去識別化到無法直接或間接辨識特定個人後，就不算個人資料。
- 在隱私權政策中說明會把去識別化後的內容交給 AI 服務分析。
- 與 Anthropic 簽商業條款：API 資料預設不用於訓練，也可以申請零資料保留。
- 保留每次送出的遮蔽後內容，作為稽核紀錄。

**Mac mini 還有用的情況**：
1. 大型保經公司要求資料一律不能離開內網。這時提供企業版地端方案，裝在**客戶自己的機房**。
2. 用量大到雲端費用明顯高於硬體成本。
3. 需要處理無法去識別化的資料。

**程式設計原則**：
- AI 呼叫統一做成可以抽換的介面，以後要換成 Ollama 時不必改業務邏輯。
- 去識別化做成獨立模組，並附上自動化測試資料集，確保每次修改都不會漏遮。

## 6. 前台原型

檔案：[prototype/agent-portal.html](../prototype/agent-portal.html)
線上版：https://claude.ai/artifact/QHAmBiH2vjoGmJnn5AT5oT

| 角色 | 頁面 |
|---|---|
| 一般業務 | 今日、新聞彙整、客戶、建議書簡化、需求與媒合 |
| 保經公司管理者 | 商品庫、合作保險公司、業務員與用量 |

**建議書簡化流程**：
1. 上傳 PDF 並指定客戶
2. 去識別化：原文和實際送出內容左右對照
3. AI 分析
4. 逐欄確認：信心低的欄位會標示，全部確認後才能繼續
5. 產生簡化圖卡

**客戶展示模式**：一鍵隱藏佣金、內部備註、聊天切入點和其他客戶清單，方便把 iPad 直接轉給客戶看。

## 7. 建議開發順序

| 階段 | 內容 | 理由 |
|---|---|---|
| 一 | 輕量客戶管理、每日新聞、LINE 分享、多租戶與權限基礎 | 技術風險低，能馬上天天使用，同時累積客戶興趣資料 |
| 二 | 建議書簡化：去識別化、Claude 分析、逐欄確認、產生圖卡 | 價值最高，要先確認法規與文宣審核流程 |
| 三 | 需求問卷與保單媒合 | 依賴共用商品庫，建置最耗人力 |
| 未來 | 原生 App、企業版地端 AI、Oracle 對接 | 依客戶需求再評估 |

## 8. 待確認事項

1. 後端主要語言最後選 C# 還是 Node.js（看團隊熟悉度）。
2. 建議書統一資料格式要有哪些欄位，以及各家建議書常見的個資欄位清單。
3. 自製簡化說明的審核流程：要送所屬公司審核，還是平台內建主管覆核？
4. 業務員離職時，客戶資料歸屬的服務條款。
5. 訂閱方案與計費方式：每份建議書的 Claude 用量要實測，換算成每席每月的 AI 成本。
6. 共用商品庫的建檔人力，以及各保險公司資料的取得方式。
